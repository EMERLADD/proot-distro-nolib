## v0.2.0 已确认范围

v0.2.0 提供本地 rootfs 管理雏形。
本版实现名称查找、指定目录登录、执行命令、ASCII 大小写兼容及本地目录列表。
技术方案是在现有原生引擎内增加命令入口，直接调用引擎，不增加宿主解释器依赖。
使用 PDN_ROOTFS_DIR 或 HOME 定位目录，不需要 Android 包名或 Intent。
验收使用最小 guest rootfs，覆盖真实运行、参数边界、失败路径和退出码。
后文下载、镜像、安装相关需求保留为后续规划，不属于 v0.2.0 交付范围。

# PDN 发行版管理器：需求草案

状态：下列完整管理器需求仍为后续规划；v0.2.0 本地入口已实现。

## 目标与范围

在现有 proot-distro-nolib 0.1.1 引擎上提供 `pdn` 管理入口，让用户在
具备所需执行、ptrace 和文件系统能力的 Android CLI 宿主里，用发行版名称
完成安装和登录，不再手动拼接 PRoot 参数。首版面向 ARM64。

Ubuntu 是命令示例，不是产品范围限制。首批目标包含 Ubuntu、Debian、
Alpine、Arch Linux ARM 和 Kali。后续发行版应通过新增目录记录和必要的
安装适配接入。只有通过安装、登录和包管理测试的组合才能标为已支持。

## 用户操作

```sh
pdn list
pdn install Ubuntu
pdn INSTALL ALPINE
pdn install debian
pdn install arch
pdn install kali
pdn login ubuntu
pdn login KALI
pdn doctor
```

建议首版同时提供已安装列表和删除功能；具体参数在设计阶段确定。

## 验收需求

### R1 命令与名称

- 当用户输入内置子命令和发行版名称时，系统应忽略 ASCII 大小写。
- 当用户指定 `Arch`、`archlinux` 或 `archlinuxarm` 时，系统应归一到同一
  ARM64 发行版标识，并明确显示安装的是 Arch Linux ARM。
- 当参数是文件路径、URL、镜像标签或传入 Linux 的命令时，系统应保留原文。
- 当名称未知时，系统应提示受支持的名称，不下载猜测出来的地址。

### R2 发行版目录与架构

- 当用户请求安装时，系统应先解析发行版、版本通道和执行架构，再选择来源。
- 当宿主或镜像不符合首版 ARM64 条件时，系统应明确报错，不混用其他架构。
- 当未指定版本时，系统应使用目录中明确记录的默认通道，并显示实际版本。
- 当在线目录有新版本时，已安装系统应继续使用其已记录的版本和配置。
- 当新增发行版时，通用安装流程应保持可复用；特定初始化行为应独立描述。

### R3 来源选择与下载

- 当选择 rootfs 来源时，系统应只遍历发行版目录中已配置的候选来源。
- 当目录中存在国内和国外镜像站时，系统应把两类候选一并纳入探测，不按地区
  固定优先，也不承诺每个发行版都有已经验证的国内镜像。
- 当比较镜像站时，系统应以有限并发对实际下载端点发起 HTTPS 请求，测量到
  有效响应的耗时，并检查所需制品是否可用；不以 ICMP ping 作为选择依据。
- 当多个候选提供同一制品时，系统应默认选择有效响应延迟最低的可用镜像；
  探测应有超时、并发数和流量上限，支持 Range 时可用少量数据确认有效下载响应，
  不支持 Range 时也不得因测速下载整个 rootfs。具体阈值在设计阶段确定。
- 当镜像返回错误页、错误架构或不匹配的版本时，系统不得因响应快而选中它。
- 当展示自动选择结果时，系统应显示被测来源、测得延迟、不可用原因和最终选择；
  可显示小样本传输速度，但不能把它当作整个文件持续速度的保证。
- 当已选来源在实际下载中持续低速时，系统应按明确阈值重新选择候选；不能只因
  最初延迟低就无限等待。跨源续传必须先验证制品身份与服务器 Range 语义。
- 当缓存镜像探测结果时，系统应设置有效期；网络条件变化或连接失败后应重新探测。
- 当镜像超时、不可达或返回缺失资源时，系统应按有限重试策略切换候选源，
  显示原因，不无限等待，也不同时下载所有候选包。
- 当切换同一制品的镜像站时，系统应保持版本、架构和预期摘要一致。
- 当 rootfs 类型或提供方需要改变时，系统应把它作为明确的候选方案处理，
  不把内容不同的 OCI 镜像和 tar 包当作同一文件的断点续传来源。
- 当下载完成时，系统应使用可信目录/发布元数据中的摘要或签名校验内容；
  校验失败的内容不得安装，缺失校验依据时不得静默跳过校验。
- 当网络中断时，系统应保留可验证的下载状态；仅在服务端和制品标识支持时
  续传，否则重新下载。应提供进度及可理解的错误信息。

### R4 安装与记录

- 当接收受支持的 rootfs tar 包或 OCI 层时，系统应正确处理压缩、权限、
  符号链接、硬链接，以及 OCI 的层覆盖和删除语义。
- 当归档中的路径或链接会越出安装区域时，系统应拒绝相应不安全操作。
- 当安装未完成或验证失败时，系统不得把该实例标为可登录，也不得破坏已有实例。
- 当安装完成时，系统应记录发行版、实际版本、架构、来源、摘要和 rootfs 位置。
- 当目标名称已经安装时，系统应保留原实例，明确提示重复安装。
- 当多个进程尝试修改同一实例时，系统应避免同时解包、删除或改写元数据。

### R5 登录

- 当用户运行 `pdn login <name>` 时，系统应读取实例记录，自动设置 rootfs、
  假 root、内核兼容参数、loader、临时目录、必要绑定和用户环境，进入交互 shell。
- 当发行版没有 Bash 时，系统应使用可用的登录 shell，不依赖宿主 Bash。
- 当用户退出 shell 时，系统应正确恢复终端并传递退出状态。
- 当支持传入命令时，系统应保留参数边界和引号语义，不使用简单空格拼接造成双层解释。
- 当使用首批发行版时，验收至少包括 shell、DNS、文件读写，以及相应包管理器
  的索引刷新和安装一个小包；Kali 的工具完整度另行定义，不默认安装全部工具。

### R6 通用宿主与运行依赖

- 当在不同宿主 App 中运行时，系统不得依赖固定包名、Termux 私有路径或动态库。
- 当下载、校验和解包时，系统应自带所需能力，不要求宿主预装 curl、wget、tar、xz。
- 当选择数据目录时，系统应提供可配置的宿主私有目录，并验证必要的文件系统能力。
- 当运行 `pdn doctor` 时，系统应检查引擎、架构、目录、ptrace 和 loader 等条件，
  明确区分宿主限制、网络故障和发行版问题。
- 当宿主不允许启动工具本身时，该工具无法在进程内修复启动权限；“通用”不表示
  所有具备 shell 的 App 都拥有相同的执行能力。

## 来源候选及核查依据

这些是候选渠道，尚未对所有 rootfs 做下载与运行验收。

| 发行版 | 候选来源 | 默认通道建议 |
|---|---|---|
| Ubuntu | Ubuntu Base ARM64 rootfs；可另定义官方 OCI 候选 | 经验证的 LTS |
| Debian | Docker Official Images 的 Debian ARM64 镜像 | stable |
| Alpine | 官方 aarch64 minirootfs | stable |
| Arch | Arch Linux ARM Generic AArch64 rootfs | rolling |
| Kali | 官方 Kali 容器渠道；安装前核实所选标签的 ARM64 manifest | kali-rolling |

## 现有代码与缺口

现有 `src/pr-cli` 已包含 CLI 命令、HTTP/TLS、SHA-256、部分压缩与 tar 解包、
OCI 架构选择与层处理、安装记录、登录参数构建，可作为复用基础。

仍需评估和改造：App 路径耦合、BusyBox 外部调用、大小写规则、可维护的发行版
目录、多源选择、断点续传、安装事务与锁、不同 rootfs 初始化、登录参数语义。
当前源码识别某种文件扩展名并不等于已经实现其解压能力。

## 待确定的产品选择

1. 交付允许 `pdn` 管理器与现有引擎一起打包，还是要求一个物理可执行文件。
2. 默认版本是否采用以上 LTS/stable/rolling 策略；是否首版就支持指定版本。
3. 首批五个发行版是否全部作为第一版验收门槛，或分批交付但保持同一目录机制。
4. 默认数据目录，以及迁入现有手工安装 rootfs 是否进入首版。

桌面/VNC、一键安装 Kali 全工具集、跨架构模拟、完整 systemd 启动、自动系统升级、
备份迁移和任意第三方容器的通用运行，暂不计入首版，等待后续讨论。
